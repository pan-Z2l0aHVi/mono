Internal change: no published package is affected, and `@greypan/interweave` is deliberately not bumped — a bump there would make the next merged version PR produce a desktop release.

Workflow topology now has one declaration: `.github/scripts/ci-topology.mjs` records every workflow's triggers, permissions, job `needs`/`if`, release-branch literal, desktop build matrix, declared install surface, step `if:` guards and step `id:` declarations, and `scripts/ci-topology.test.mjs` reads the real YAML and compares field by field. Every `steps.<id>.` reference now has to resolve to a declared id, and the id that gates the failure ledger has to belong to the step named `Test` — in Actions a reference to a missing id is not an error, it is a step that quietly never runs. `ci.yml` no longer triggers on `push` to `main` — the repository is squash-only with a strict required status, so that run re-validated a tree that `pull_request` had already validated; `workflow_dispatch` stays as the on-demand trunk check. `ci.yml` also gains explicit `permissions: contents: read`.

`.github/scripts/detect-versioned-packages.mjs` now passes `--find-renames` and reads the base manifest from the rename's old path. Git detects renames by default, so a package directory move arrived as `R` and the previous `--diff-filter=AM` dropped it silently: the new npm name was never published while CI stayed green. Publishing is now keyed on the `(name, version)` identity, so a renamed package is published once and a pure directory move produces nothing.

The CI test task captures its output and, when that step fails, `.github/scripts/record-test-failures.mjs` writes the vitest `FAIL` lines to `$GITHUB_STEP_SUMMARY` and uploads the raw log plus a machine-readable list as a 1-day `ci-test-output-<run>-<attempt>` artifact. The recording steps are guarded by `steps.test.outcome == 'failure'` rather than a bare `failure()`, because `failure()` also holds when an _earlier_ step went red — a lint failure would then skip `Test` and still produce a ledger entry with no test log behind it. They never change the verdict; they exist because GitHub retains nothing retrievable from earlier attempts, so a flake ledger can only start from instrumentation that lands now.

`scripts/ci-measure.mjs` (`pnpm measure:ci --days=14`) is a read-only cost ledger over the Actions runs API: per workflow it prints runs, wall-clock minutes, the trigger-event mix and same-`head_sha` duplicate validation. The two columns price different things — under squash-only merges a `push` run on `main` carries a fresh sha for an already-validated tree, so sha-keyed redundancy cannot see it and a removed trigger is measured by the `push` column. Traps this script exists to stop re-litigating are recorded in its header (`name=` silently ignored, `total_count` jitter, `%3E` encoding for `created`, code-unit vs code-point slicing) and pinned by `scripts/ci-measure.test.mjs`.

`scripts/ci-flakes.mjs` (`pnpm flakes:ci <dir>`) is the read side of the failure ledger: it walks downloaded `ci-test-output-*` artifact directories, merges every `test-failures.json` per test — suite-level load failures fold onto their file instead of forming one row per collect error — and ranks by distinct runs before attempts, since two attempts of one run only prove the test went red twice. An unreadable artifact is reported and skipped rather than emptying the board. It deliberately never concludes that a test was fixed: the ledger is written only on failure, so absence carries no information. The step summary now points at this command.
