Internal change: no published package is affected, and `@greypan/interweave` is deliberately not bumped — a bump there would make the next merged version PR produce a desktop release out of a change that touches nothing the build reads.

`apps/interweave/build/windows/msix/` is deleted. The two XML files came with the Wails project template and nothing consumed them: `build/windows/Taskfile.yml` gates its `package` task on `FORMAT = nsis` and otherwise fails with "MSIX packaging is not supported by Wails 3 CLI 3.0.0-alpha2.122.", so no task, workflow or release path ever opened the directory — which is also why their contents were wrong rather than merely unused. `Version="0.1.0.0"` sits in both files, outside the version write set in `apps/interweave/scripts/sync-version.mjs` (`build/config.yml`, the two plists, `wails.exe.manifest`, `info.json`), so it never tracked a released version; `app_manifest.xml` declares `ProcessorArchitecture="arm64"` while the only Windows artifact either pipeline builds is `interweave-windows-amd64`; and the two `Logo` values (`Assets\StoreLogo.png`, `Assets\AppIcon.png`) name files the repository does not contain. A second, stale copy of the package identity next to the authoritative one is how future MSIX work starts from the wrong file — regenerate it from the then-current toolchain once Wails supports the format instead.
