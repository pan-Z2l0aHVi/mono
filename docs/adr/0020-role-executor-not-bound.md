# ADR-0020: Role 不绑定执行体，建会话前当场选定

- **Date**: 2026-09-30
- **Status**: 已接受
- **Amends**: [ADR-0010](0010-agent-role-orchestration.md)、[ADR-0011](0011-agent-model-binding-and-effort.md)、[ADR-0016](0016-implementation-supervision.md)
- **Amended by**: [ADR-0004](0004-progressive-agent-context-architecture.md) 的「角色执行体绑定补充」一节不再描述默认绑定

## 背景

ADR-0010 在「替代方案」里明确否决过这一条：

> **不做执行体绑定，保持「任一模型/CLI 承担任一角色」**：灵活，但无法为固定的角色-执行体协作链路建立稳定预期；不采用。

于是 skill 里落了一张写死的表：Manager / Designer / Supervisor / Reviewer 用 Claude Code，Lib Coder / Biz Coder 用 Codex CLI。这张表带来三个问题。

第一，它是一层**无人选择、也无人负责**的约定。表里的分配不是谁按当前任务判断出来的，是几个月前一次决策的产物，之后一直原样生效。

第二，它和「按任务选模型」的做法天然冲突。ADR-0014 取消了模型与思考强度的默认分档，理由是分档会过期、会误导。那么把同样的逻辑用在执行体上——唯一多出来的考量只是「稳定预期」——却留着不动，是不自洽的。

第三，也是这次改动直接暴露的：**这张表在两个 ADR 里被当作现行事实复述**（ADR-0004 整节、ADR-0016 的权限段），Reviewer 与 Supervisor 的 Role 文档也各自写着「默认执行体是 Claude Code」。表一改，这些复述就全部变成假话，而它们散在四个文件里，没有任何一个校验器会发现。

至于当初否决的理由——「无法为固定的角色-执行体协作链路建立稳定预期」——现在有一个不同的答案：**预期不必按角色建立，可以按轮次建立。** 执行体在编排开始后、真正要为某个 Role 建会话时才定，选定结果记进本轮编排记录，于是这一轮参与者的执行体是完全确定的、可复盘的，事后能查「当时为什么让 Reviewer 跑在 codex 上」。原来那层「固定链路」提供的预期间隔被一轮一问替代了，而它更贴合实际：下一轮完全可能换。

## 决策

1. **Role 不绑定执行体。** skill 里的绑定表删掉「默认执行体」这一列，只保留 Role 与责任。ADR-0010 那条「不做执行体绑定」由此从「被否决的备选」转为现行决策。

2. **Manager 不占这个选择。** 谁执行 `/herdr-agents`，谁就是本轮的 Manager，执行体就是它当下所在的 CLI。不为 Manager 单独提问，也不要求它是某一种。

3. **其他 Role 在建会话前当场问。** 由拆分结果决定要开哪些会话（几个 Coder、要不要 Designer、Supervisor 分数够不够、Reviewer 按级别派不派），这些照常推导；**每当真要为某个 Role 建会话时才问一次**，没派上的 Role 不问。同一步要开多个会话时（多个 Coder、Reviewer 与 Coder 同批）合并成一次交互提问，不拆成多轮。

4. **选项运行时发现，不写死名单。** 先跑 `herdr agent` 读出该机 `kinds:` 一行再构造选项。新装一种 kind 自动可用，也不会推出一个启动不了的选项——这正是写死 `zcode` 这类名字的风险：它不在本机已安装列表里，选到就失败。

5. **提问走 `AskUserQuestion`，因此受其 4 选项上限约束。** 给 2–3 个最常用 kind 加一个「手动输入自定义」占位，并在问题描述里附上 `herdr agent` 读到的完整 kind 列表，让用户直接输入列表外的任何一个。该工具始终附带一个「Other」自由输入，与这个占位是同一件事，不必依赖客户端版本一定提供它。

6. **选定结果按 Role 记进本轮编排记录**，同一轮内复用同一 Role 的上一次选择。执行体与 Role 相互独立：任一 kind 都能承担任一 Role。Supervisor 与其他 Role 用相同的权限参数启动，它的只读边界来自 Role Contract 与 Manager 的 handoff，与启动参数无关——这条来自 ADR-0016，不因本决策改变。

7. **启动参数按 kind 查，不套用固定表。** 启动前按上游 `herdr` skill 发现当前 kind 及其原生参数。skill 保留 Claude Code / Codex CLI 两行作为常见样例并注明以实际输出为准。

## 后果

- 删掉了 8 处分散复述「默认执行体」的位置（skill 表、两个 Role 文档、四份文档指针），Role 文档重新满足 ADR-0004「不复制执行体选择规则」的要求——改动前 `reviewer.md` 与 `supervisor.md` 其实已经违反了这条。
- `scripts/validate-context.mjs` 不受影响：ADR-0012 已删除绑定表镜像校验，这里没有任何机器守卫会因本次改动失败。**代价是绑定关系从此完全无人校验**——这是接受的，因为本决策取消了需要校验的东西。
- 编排开始时多一次交互。多开几个 Coder 就多几次提问，但它们合并在同一步内，且省掉了「选错执行体后重开会话」的成本。
- 执行体成为**每轮可变的编排输入**，因此它属于编排元数据，落 `$TMPDIR/herdr-agents/reports/` 的编排记录，不进 Task Packet，也不进 task state——沿用 ADR-0017 对编排元数据的处理。

## 被否决的备选

- **保留绑定表，只把它挪进 skill 不再进 ADR**：文档与实现仍会分叉，且 ADR-0010 的否决理由依然成立——只是被藏起来了。
- **在拆分前一次性问完所有 Role 的执行体**：会问到本轮根本用不上的 Role（Reviewer 是否派由 T0/T1/T2 路由决定，Manager 拆分前不知道），答了作废。
- **让 Manager 自行决定、不问用户**：执行体差异直接影响成本、模型能力和 MCP 工具可用性（本仓的 `chrome-devtools-mcp` 只配了 Claude 侧），Manager 无从判断用户想要哪一种。
