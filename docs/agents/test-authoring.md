# 测试用例编写策略

本文件讲测试用例的编写策略：写什么和怎么写。环境、命令与验证选择由 `verification.md` 承担。

1. 不要为每一次 UI 变更自动创建测试。

2. 只有当测试能防止一个合理且真实的回归时，才添加测试。

3. 优先测试：

   - 业务逻辑
   - 状态转换
   - 用户交互
   - 可访问性契约
   - 关键用户流程

4. 纯展示层的变更：

   - 不要加单元测试
   - 不要断言具体 CSS 属性
   - 不要断言 DOM 结构
   - 除非有明确理由，否则不要加 Snapshot 测试

5. 优先写面向行为的测试，不写面向实现细节的测试。

6. 不要测试：

   - 精确像素尺寸
   - 精确 CSS 值
   - 内部 class 名称
   - 内部组件状态
   - 用户不依赖的 DOM 结构

7. 仅对稳定且高价值的 UI 做视觉回归测试。

8. 每个测试都要能回答：它能防止什么真实的回归？

9. 说不出具体的回归风险，就不要加这个测试。

10. 优先扩展已有测试，不创建功能重复或高度重叠的新测试。

11. 不要为了提高覆盖率加低价值测试。覆盖率是参考指标，不是测试数量和质量的目标。

12. 测试必须稳定、可维护，并反映真实的产品行为。不要加容易 flaky 的测试，除非这种不稳定性本身就是要验证的产品行为。

13. 当代码或行为变化让已有测试失去价值时，删除或重构这些测试，不要为了让测试通过而改生产代码。

14. UI/UX 判断优先关注用户可感知的行为、可访问性和关键视觉回归。不要试图把所有设计决策都转成自动化断言。

15. 测试用 Arrange、Act、Assert 结构。每个测试只验证一个行为，保持独立。描述用中文。

16. 仅在需要断言调用时用带类型的 `vi.fn<Type>()`，并等待确定性的生命周期信号，不要用任意超时。

17. 保持行为不变的重构，编辑前先记录现有行为清单。保留行为或获得移除审批后再变更，并更新相应的测试和文档。
