# 测试用例编写策略

本文件讲测试用例的编写策略：写什么和怎么写。环境、命令与验证选择由 `verification.md` 承担。

- 只为能防止真实回归的测试买单。说不出具体回归风险、或只是为了提高覆盖率，就不要加；优先扩展现有测试，不建功能重复或高度重叠的新测试。
- 优先覆盖业务逻辑、状态转换、用户交互、可访问性契约与关键用户流程。UI/UX 判断以用户可感知的行为、可访问性和关键视觉回归为准，不把设计决策全部转成自动化断言。
- 优先写面向行为的测试，不写面向实现的测试。纯展示层变更不加单元测试，不断言具体 CSS 属性、像素尺寸、内部 class、内部状态或用户不依赖的 DOM 结构；展示层默认不加 snapshot，视觉回归只用于稳定且高价值的 UI。
- 测试必须稳定、可维护，反映真实产品行为。容易 flaky 的测试不加，除非不稳定性本身就是要验证的产品行为。
- 代码或行为变化让测试失去价值时，删除或重构测试，不要为了让测试通过而改生产代码。保持行为不变的重构，先记录现有行为清单，保留或获得移除审批后再变更，并更新测试与文档。
- 测试用 Arrange、Act、Assert，每个测试只验证一个行为并保持独立；描述用中文；只在需要断言调用时用带类型的 `vi.fn<Type>()`，等待确定性的生命周期信号，不用任意超时。
