# 方案对抗性评审

实施方案（设计文档、重大技术决策草案）定稿前接受对抗性评审，目标是让缺陷止步于纸面。
评审对象是方案本体；实施开始后的代码复审纪律见 [`review.md`](./review.md)，两者共用循环收敛纪律。

## 分轴：内部一致性与外部假设

对抗性评审能验证的是内部一致性：契约冲突、组件边界、失效路径、安全与并发隐患。它验证不了
外部假设——CLI 参数行为、协议 schema、环境差异——这些只有实测能锚定。方案须显式标注外部
假设；评审通过不等于假设成立。假设在定稿前或实施第一步用最小探测钉死，实测结果回写方案；
实测推翻的假设按新证据改方案，不按评审共识保留。

## 循环与收束

- 评审发现编号并合入方案本体（补丁式修订），不散落评论；每轮以补丁清单与遗留项结束。
- 循环收敛沿用 [`review.md`](./review.md#报告回写与复审) 的「复审循环的收敛」三条（封顶、
  复现即重设计、确定性验证先行——设计期的确定性对应外部假设实测）；封顶后仍有 Block 级未处置发现即 No-Go。
- trade-off 类争议升级用户拍板收束，不靠辩到饱和；拍板结论连同理由合入方案或 ADR。
- 终稿带显式结论（Go / No-Go）与已合入的补丁清单；没有显式结论的方案不进入实施。
