# 开发与协作工作流

本文件规定从方案到合并的工作顺序、用户授权边界与跨阶段恢复。任务分级与本地台账见 [`.agents/skills/task-ledger/SKILL.md`](../../.agents/skills/task-ledger/SKILL.md)，PR 审查见 review.md，验证选择见 verification.md，提交规则见 commit.md。需求拆分与 owner/worktree 分配由外部编排层负责，仓库 CLI 不承担编排。

## 从方案到合并

工作顺序是方案 → 实施与测试 → 提交并创建 PR → 独立 review 与按影响选择的端到端验收 → 修复复审 → 核对合并前证据并经用户授权后合并。实施、测试与提交可以小步交错；PR 阶段的独立 review 与验收可以并行。端到端验收按变更影响选择，不要求所有任务执行。

合并前的 review、测试与 CI 证据必须对应当前 PR base/head；PR CI 复检不替代实施阶段的验证证据。这里的顺序不对应 task CLI 相位，也不把结论写回本地台账。审查与验证细节由 review.md 和 verification.md 规定。

## 预授权操作

以下操作无需逐次确认，可以直接执行；本次改动造成的失败也可以直接修复：

- 只读调查：读取工作区文件，运行状态查询与只读检索。
- 运行仓库既有的测试、检查与构建，并重跑受影响的项。
- 清理系统临时目录中的临时内容。
- 结束本任务启动且启动记录能从本任务 worktree 对应的唯一 MCP/启动服务追到浏览器父子链、PID 与独占 profile，并且每一环都能复核的浏览器进程。共享 codex app-server 的共同父进程、PID 与 profile 自洽或浏览器 CWD 都不足以单独确认归属；精确 worktree CWD 仅用于定位本任务的 MCP/启动服务。无法唯一确认归属时，先按 [`怎么取得这个授权`](#怎么取得这个授权) 取得用户授权并确认目标。

以下操作仍须逐次获得用户明确授权：

- 改变仓库历史、分支或远端状态。
- 改变仓库级架构与共享配置：依赖与供应链、根级脚本与配置、CI 与 workflow 定义。
- 调整或新增任何执行超时、等待上限或重试上限都须先取得用户明确授权，范围包括 CI/workflow 的 job `timeout-minutes`、测试运行器与 E2E 的 timeout、构建与脚本中的 timeout 和重试次数/累计等待，以及工具链或任务编排层的等待上限。不得为了让失败的检查变绿而放宽这些上限，应先根据失败证据修复原因。
  - 申请须写明目标值、当前或原有上限（新增且无旧值时注明「无」）、相关 run 的实际耗时及对应日志/阶段证据，并说明目标值依据。
  - 若申请延长或放宽现有限制以容纳本应完成的工作，须证明失败 run 用尽原上限后仍未完成该工作，日志或阶段记录应表明原因是上限不足而非其他故障。同一任务路径有多次可比运行时，按最慢一次的实测耗时评估，不得以最快或缓存热的 run 推断。
  - 若申请收紧限制，须说明目的，并提供正常路径的实测耗时来证明新值不会中断有效工作。
- 发布或对外交付。
- 读写凭证、密钥与本地环境配置。
- 可能丢失改动、删除非临时内容或其他不可逆的破坏性操作。

### 怎么取得这个授权

需要授权时，直接调用 [`request-authorization` skill](../../skills/request-authorization/SKILL.md)：以交互式弹窗提交请求，弹窗正文四项说明、选项要求、同意语义与回合收尾自检都由该 skill 拥有。客户端不支持 skill 调用时，读该 SKILL.md 按形状执行。

弹窗只是呈现选择，不代替授权本身——用户点了推荐项才是授权，**没有回答不等于同意**。

这条是全文所有「需用户明确授权」「先询问用户」的唯一机制来源：其他文档只声明该处需要授权并指向这里；请求的形状与执行由 request-authorization skill 承载。操作系统的权限对话框不经过本流程。

## 跨阶段恢复

- 范围变化时，先更新 Task Packet（模板与边界见 `task-ledger` skill）再继续实施。
- 验证失败时保留真实输出，修复原因并重跑受影响的检查；证据必须对应当前 base/head。
- 中断恢复以 Task Packet 与真实 Git 状态为准，台账（见 `task-ledger` skill）只辅助归属和进度，不能补造已通过的验证、review 或 CI。
- 合并前仍须取得明确授权；授权前保留可检查的 diff 与证据。

release playbook、changeset 与发布链验证见 release.md。流程拆分、PR 跟进与 worktree 回收由编排层负责。
