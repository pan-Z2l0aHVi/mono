# 测试策略

1. 不要为每一次 UI 变更自动创建测试。

2. 只有当测试能够防止一个合理且真实的回归问题时，才添加测试。

3. 优先测试：

   - 业务逻辑
   - 状态转换
   - 用户交互
   - 可访问性契约
   - 关键用户流程

4. 对于纯展示层的变更：

   - 不要添加单元测试
   - 不要断言具体 CSS 属性
   - 不要断言 DOM 结构
   - 除非有明确理由，否则不要添加 Snapshot 测试

5. 优先编写面向行为的测试，而不是面向实现细节的测试。

6. 不要测试：

   - 精确像素尺寸
   - 精确 CSS 值
   - 内部 class 名称
   - 内部组件状态
   - 用户不依赖的 DOM 结构

7. 仅针对稳定且高价值的 UI 使用视觉回归测试（Visual Regression）。

8. 每个测试都必须能够回答：

   > “这个测试能够防止什么真实的回归问题？”

9. 如果无法明确指出具体的回归风险，则不要添加该测试。

10. 优先扩展已有测试，而不是创建功能重复或高度重叠的新测试。

11. 不要为了提高测试覆盖率而添加低价值测试。测试覆盖率是参考指标，不是测试数量和质量的目标。

12. 测试必须保持稳定、可维护，并且能够反映真实的产品行为。不要添加容易产生随机失败（flaky）的测试，除非该不稳定性本身就是需要验证的产品行为。

13. 当代码或行为发生变化导致已有测试失去价值时，应删除或重构这些测试，而不是为了让测试继续通过而修改生产代码。

14. 对 UI/UX 的判断应优先关注用户可感知的行为、可访问性和关键视觉回归。不要试图将所有设计决策转化为自动化断言。
